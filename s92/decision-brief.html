The brief, as a decision

Four choices, in the order in which they have to be made. Each one has a question behind it, a suggestion that implements it, and a consequence if it is not made. Nothing below has been decided on your behalf.

Choice 1 — do we buy prices?

QuestionQ-101. Which feed, at what latency, at what licence cost?
SuggestionS-101. Licence one point-in-time archive and replay a completed season.
If yesevery market-relative metric becomes computable: vig, fair value, closing-line value, edge
If nothe project stays a prediction exercise; no strategy can ever be called skilled
Cost of delayevery week of the season is a week of prices not captured, and prices cannot be bought retrospectively

Recommendation: yes, and this is the only purchase that unlocks the rest.

Choice 2 — do we buy participation data?

QuestionQ-103. Are we entitled to store and re-price snaps, routes and targets?
SuggestionS-105, then S-106 to use realised snap share instead of club charts.
If yes"a starter is out" becomes "his replacement costs N points", and the depth requirement becomes quantitative
If nothe depth page stays a count of bodies, and prop markets stay unpriceable

Recommendation: yes, but second. It only pays off once prices exist to value it against.

Choice 3 — do we fund the leaderboard?

QuestionQ-110. What does it pay, to whom, on what schedule?
SuggestionS-111. Write the budget, tiers, eligibility and anti-gaming rules before the first entry.
If yesthe competition has an incentive structure and the gates have teeth
If nokeep the registry as a research log; drop the reward language so the page does not promise what it cannot pay

Recommendation: write the rules now even if the budget is zero. An unfunded but well-specified board is more honest than a funded one with no rules.

Choice 4 — one dashboard or many?

QuestionQ-112. Which page owns each number?
SuggestionS-112 and S-116. A metric ownership table, and one landing page with category navigation.
If yesa reader can trust that two pages will not disagree, and the archives stay as archives
If noevery number needs an owner named next to it, forever

Recommendation: yes. This dashboard is built that way on purpose; it links rather than restates.

The honest summary

The repository has one fully verified dataset, one partially verified dataset, one stale dataset and one absent dataset. The highest-value work is not a better model; it is storing better data. If you approve only one thing, approve S-102: store every injury filing with its timestamp. It costs nothing, it fixes an error that is already visible, and it is the prerequisite for the only signal family where this project is currently strongest.
